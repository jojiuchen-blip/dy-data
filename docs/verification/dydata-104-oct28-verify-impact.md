# DYDATA-104：普通核销影响范围核查（2026-10-28）

此缺陷属于104已授权的运行可靠性与全票验收范围。当前为开发与验证记录；没有通过本记录取消生产任务、放宽发布检查或扩大历史财务更正授权。

## 已验证的原因

生产旧版本9b1feb8与候选b3acd4d1/b5df08fd的相关捕获、选券和局部计算函数一致。普通verify影响同时携带券ID、核销ID及POI上下文；选券查询将它们用OR连接，选入该POI所有历史核销券和意向订单券。不同64条impact页会重新读取相同POI，页内去重无法防止页间重复。有效券的结算明细会删除重建，费用指纹不变只避免新增费用版本。

精确日任务的只读汇总为5,931条影响：order2,460、coupon2,263、clue871、verify337，没有store_poi_mapping影响。337条verify均为有明确券号的新插入：247个核销POI，加上订单意向POI后扩到289个POI。按实际分页位置，最后6页verify数量为38/64/64/64/64/43，POI数量为43/75/60/62/70/49；54个POI跨页重复，合计359个页内POI成员关系。

03:13只读观察到该任务已更新62,862条结算明细，仍在运行；新费用结果只有每方向36条。不能把所有非337券都称为误选，因为另有合法订单和券影响；也不能把全库规划估计行数当作本任务完成比例。私有原始输入包含业务ID，仅保存在受控证据目录，未提交仓库。核销影响输入SHA256：`d7d33cff1bbd65558c3d99b6cf429840d5d86167ee074153d63d6d86e895d25d`。

独立合成复现：单条明确指向1券的核销影响会选中3券（增加意向POI时4券）；两个同POI事件同页处理3券，分两页处理6次但只有3个不同券。旧版与候选相同。既有相关5项测试通过，但没有覆盖同POI无关历史券隔离及跨页扩大计算。

## 修复边界与验收

- 普通核销按准确的旧/新券身份及核销身份确定实际影响；POI上下文保留用于门店、月份发布维度，不用来扩大普通事件的选券范围。
- 真正门店POI映射变化保留完整旧/新门店、核销POI及意向POI历史范围，不增加任意日期截断。
- 没有直接券身份时可以精确回查当前核销记录与历史结算明细的verify_id；不以订单上下文扩大兄弟券。仍无法定位的影响明确计数并保留原始证据，不宣称已算出该券费用。
- `completed`沿用“本轮影响流已消费”的语义，不新增“所有身份/金额完整”的含义；未解析计数须保留到任务checkpoint。
- 不建立全日券ID内存集合，不改变计算公式、保护账务、锁、批量大小或超时。不同合法事件确实影响同券时仍可正常重算。
- 测试覆盖同POI历史券隔离、意向POI、旧新券/核销身份、精确回查与未解析计数、映射历史闭包、跨页及实际PostgreSQL查询行为。

核销状态捕获另已核查：虽然canonical字段元组未直接列verify_status，`_canonical_values`会加入归一状态，不能据元组缺项误判状态变化不捕获；本修复不改repositories。

## 当前结果

六组专项初次回归102项通过、零跳过/失败（46.32秒），包括真实PostgreSQL的影响读取和增量结算。主线程独立复核运行初次新增20项，全部通过（13.27秒），其中9项为真实PostgreSQL用例；实际非零已锁账账单的金额、费用版本、当前指针及调整记录保持不变，同POI无关券的完整快照不变。

主线程进一步发现完全空身份的独立verify页可能漏掉发布维度。新增SQLite/PostgreSQL各覆盖成功及失败fence的4项测试，在修复前准确复现2项失败；修复后六组共106项全部通过（46.07秒）。成功fence保留独立月份/门店，失败fence不暴露闭包或推进游标；新增专项因此共24项，其中11项真实PostgreSQL。

CI为此增加独立的临时PostgreSQL 16服务，并将新增测试纳入104的零跳过闸门；XML还必须证明11项PostgreSQL用例全部执行成功。该服务只有合成测试数据，不连接生产数据库。`git diff --check`、套件锁、全局文件与S4路由检查通过。

发布合同静态检查发现腾讯云路径尚未同步新增测试；两条工作流现已使用同一数据库服务、环境与完整测试/收据规则。新增收据校验反例覆盖缺项、错误模块、跳过、失败与错误。主线程执行发布覆盖及Compose配置回归共213项通过（7.93秒），不能用此前单一路径通过替代这次修正后的完整目标CI。
