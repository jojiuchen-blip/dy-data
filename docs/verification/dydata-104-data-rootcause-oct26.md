# DYDATA-104 归属诊断、OpenAPI 历史区间与月结计数修复

关联：[DYDATA-104](https://linear.app/keith-lim/issue/DYDATA-104)、[T3.1](../plans/delivery-plans/sub-delivery-plan-dydata-104-followthrough-T3.1-release-acceptance.md)。实现基于 `6ac6e44035d659d87343369dc89380417ec83dd7`，与商品类型和默认账期 [PR63](https://github.com/jojiuchen-blip/dy-data/pull/63) 分开交付。

## 问题及行为

1. 普通双费解析失败只记录无法归属，缺少真正失败节点。新增共享诊断引擎，费用异常保留经过白名单和条数限制的账号、状态、候选店、日期及拒绝原因。业务调用保留原有 autoflush；公开只读诊断使用 no_autoflush。历史交易裁决优先级保持。
2. OpenAPI 原始行的 `account_id` 是职人标识，后台明细行的同名字段可表示门店标识。旧昵称解析把前者直接当店查，导致已有有效 UID、完整历史区间和 POI 映射的交易失败。
3. 月结 `issueCount` 错用了调整记录数，零调整会把非零费用阻断报成零。改为真实 `blocked_count`；成功发布仍不表示所有来源均具有计费资格。

## 归属修复边界

只有原解析没有有效门店候选时才增加 OpenAPI 路径。直接账号无效、有效期冲突、旧状态冲突、已有单店或多店的决定保持优先。要求：

- 订单原账号、原始 `account_id`、payload `craftsman_uid` 精确一致；可选 settlement ID 不能冲突；采集来源 key 与原始身份一致。
- payload/原始行的 POI 和状态一致；状态 2/105，或状态 5 且完整历史区间覆盖销售瞬时。106 和其他状态拒绝。
- 起止字段必须完整、合法、正数、顺序正确，按秒或毫秒精确转换 UTC；不把数据库写入时间当绑定日期，不猜缺失端点。
- POI 只能映射一个有效门店；同 UID 存在不合格绑定、多条覆盖绑定或多门店都保守拒绝。

修复只返回销售归属，不写账号维表有效期、当前绑定或权限，不改独立打榜。通过归属之后仍检查商品、费率、实收、退款、核销与账单保护。没有迁移，也没有增加人工逐券例外。

官方字段来源：[职人信息列表](https://partner.open-douyin.com/docs/resource/zh-CN/local-life/develop/OpenAPI/general-capabilities/employee-info/query-info-list)；既有状态合同见 [身份源记录](../devlog/20260911_ranking_source_identity.md)。结束字段按绑定区间使用，不直接宣称为实际解绑事件。

## 数据交接和剩余工作

逐笔数据、全量互斥分类、分月影响、金额与旧账单来源差异均在 DYDATA-104 的受控交接材料中，禁止把真实业务 ID、私人来源文件或凭据提交仓库。

原人工裁决的完整性核验与历史归属的独立证据充分性是两项不同检查；缺少原始编号桥或销售当时绑定证据时保持未知。暂停的券组不因本修复获得补录授权。首次漏记、已确认来源漂移、金额差异和月份更正分开处理，不直接改确认/开票事实或挪月。

上线后需要按批准范围正式重算、校验费用和保护指纹、构建账单与发布，再验证页面/导出。T3.1 和 DYDATA-104 继续进行中；本轮代码与只读核查不等于生产数据已全部修复。
