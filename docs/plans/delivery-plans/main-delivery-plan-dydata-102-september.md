# DYDATA-102：2026-09 账期生成与对账修复

> **版本**：v1
> **发布日期**：2026-10-08
> **前序版本**：无
> **适用范围**：DYDATA-102；在 2026-10 形成 2026-09 推广服务费账期数据
> **参与角色**：DSH 执行 / Codex 技术验收 / 用户业务审核与验收
> **开发模式**：团队协作（AI 执行、人类 Owner 审核）
> **执行约束**：不伪造金额；仅依据有效核销月份和有效分佣结果；已确认、开票、争议或锁账的财务事实不可自动覆盖；生产账单只生成待确认版本，不自动确认或开票。
> **目标**：查明 2026-09 合格分佣来源未出现在正式账单的原因；修复必要的生成触发链路，并在 2026-10 形成可对账、可查、可导出的 2026-09 当前账单。
> **当前需求基线**：Linear DYDATA-102（In Progress）；已观察到 2026-09 财务推广费总览 ¥0.00 / 0 行，榜单累计金额属于 2026-08；是否存在 2026-09 合格来源尚须生产只读核验。
> **上游发现结论**：`collect-upstream-context.mjs` canProceed=true，slug=dy-data；发现大文件提示，已只读相关章节。

## 0. 本计划使用指南

1. 先读 DYDATA-102 与本计划，再打开 T0.1 子计划。
2. DSH 执行代码及测试，Codex 独立检查根因、diff 和验证证据。
3. 先在目标环境只读核对 2026-09 来源，再决定是否需要代码修复或运行已有生成流程；生产写入仅限经校验的 2026-09 待确认账单。

### 0.1 PRD 加载约束

- 以 `docs/prd/mainprd-dy-data.md` 为全局入口。
- 仅加载本任务列明的门店结算、推广服务费与订单费用明细章节，以及账单/API/Schema 相关子文件。
- 费用账期按有效核销月份，不以销售月份或累计值代替。

### 0.2 读前门禁 / AI 自检清单

- Linear DYDATA-102、主计划、看板、T0.1 状态一致。
- T0.1 必须经人类 Owner 明确审阅通过并转为“待开发”，才可进入代码实装。
- DSH 工作区连接恢复；若仍不可用，执行主体需按用户偏好先尝试恢复，再报告替代执行方式。
- 生产数据核查先脱敏，只输出月份、行数、费用方向和分金额。

### 0.3 完成前验证门禁

- 有效来源行数/金额、当前投影、账单、列表、总览、导出使用同一 2026-09 账期及费用方向对账。
- 覆盖重复重跑、冲正/退款、已保护账单与 2026-10 边界。
- 定向 pytest、全量 `python -m pytest`、Web build（若前端受影响）、`git diff --check` 通过。
- 如需代码修复，部署后只读复核 2026-09 总览、明细和导出；无合格来源时不得制造非零金额。

## 6. 风险与应对

| 风险 | 影响 | 应对 | Owner | 状态 |
|---|---|---|---|---|
| 9 月没有合格来源 | 不能形成非零推广费账单 | 用有效来源筛选行数/金额确认；不制造数据 | DSH → Codex | 待核验 |
| 触发全局结算重建影响其他未锁账期间 | 其他期间可能产生新待确认版本 | 先审查触发范围与待保护账单；若现有入口范围过宽，先实现可审计、幂等的月份范围，不盲目触发 | DSH → Codex | 待评估 |
| 历史确认、发票或异议事实被重写 | 破坏财务证据 | 复用生成器保护逻辑；对受保护期间只读跳过 | DSH → Codex | 持续控制 |
| 账期口径错用销售月份 | 费用跨月错记 | 依据有效核销月及既有 API/Schema 合同验证 | DSH → Codex | 已明确 |
| DSH 文件夹选择接口不可用 | 无法通过用户指定 harness 执行 | 恢复工作区连接；保持隔离 worktree，恢复前不假称 DSH 已执行 | Codex | 当前阻塞 |
