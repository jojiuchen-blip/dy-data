# 线索终态与24小时跟进规则

## 请求与范围

用户要求补齐之前遗漏的核销/退款线索关闭修复，同时实现已确认的24小时规则；“线索生成”明确指正式分配到门店。跳过Linear授权沿用。隔离分支 `fix/clue-terminal-followup`；本轮无生产写入、部署或推送。

## 根因与改动

1. 原始线索观测时间未变化时，物化过程提前跳过，连带忽略后到的订单/券/核销/退款证据。现将订单状态评估移到线索新旧判断之前，旧线索仅更新生命周期，不覆盖身份或门店锚点。
2. 终态关闭主线索、当前轮次及中心投影；操作入口再次读取终态证据，禁止新增跟进、换店或分配，保留既有跟进记录。
3. 排行榜实时读取、排行榜快照及门店分配评分共用 `clue_followup_metrics.py`。起点为 assigned_at，未满24小时入分母；早期核销1/1、早期退款有跟进1/1无跟进0/0。核销分项保留成熟样本。
4. 当前订单状态优先于旧线索状态；分页物化不重复读取同订单全部线索。查询按500订单分批。
5. 新版本指标隔离旧排行榜快照与计划评分快照键，页面文案同步。

## 历史修复操作（未在生产执行）

默认预演：`python scripts/repair_clue_terminal_states.py --batch-size 100 --max-batches 20`。
可用 `--order-id` 限定订单，使用输出的 `after` 作为 `--after` 继续下一页。预演回滚每页；只有 `--apply` 才提交。工具只处理已存在主线索的终态，不重写原始线索、不创建分配、不删除跟进。
发布前应备份并检查预演数量；发布后再授权执行历史修复并通过既有任务刷新新版本排行榜/评分。历史业务终态时间缺失不伪造24小时证据。

- 第一轮状态/分配集成156通过、1失败；修复工具用例曾使用不符合有效订单语义的初始值，另有SQLite时区显示差异，已修正并复验。
- 整合专项219通过，正式分配运行流程29通过；最后的指标+终态组合41通过。
- 独立复核发现并修复：撤销核销的旧轮次回声、同券不同核销ID误排除、未知终态时间误计成绩、终态证据时钟较早导致只禁操作未关闭、修复统计字段遗漏，以及错误轮次指针跨主线索关闭。
- 接口终态时间支持秒/毫秒的数字字符串；未知实际终态时间明确标记 terminal_time_unknown 并暂不纳入指标，不以观测时间伪造业务时间。closed_at/matured_at 对缺失时间的生命周期兜底沿用原有状态记账用途，指标不读取该兜底。

- 前端最终构建通过（tsc + Vite），只有既有大包提示；套件锁、全局文件与计划结构验证通过。
- PostgreSQL专用并发测试未运行，本机Docker服务未启动；SQLite测试不能代替真实行锁验收。
