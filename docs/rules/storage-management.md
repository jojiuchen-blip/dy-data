# 通用磁盘与备份管理规则

## 适用范围

本规则适用于本项目的部署目录、数据库备份目录、日志、构建产物和容器存储。规则描述可迁移的路径与操作约束，不依赖某一种云主机或具体机器。

## 磁盘阈值与处理顺序

- 磁盘可用空间低于 15%，或低于 10 GiB 时，停止产生新的整库备份并先做容量处置。阈值可通过部署环境的 `BACKUP_MIN_FREE_PERCENT` 和 `BACKUP_MIN_FREE_BYTES` 调整，但调低阈值必须有审阅记录。
- 固定余量之外，还要预留最近一份有效整库备份大小乘安全系数（默认 150%）的空间；没有历史备份时至少保留固定余量。仅有“看起来够用”的百分比不能绕过下一次写入容量估算。
- 写入大文件前先确认校验器可用。部署默认调用当前 Compose `postgres` 服务内的 `pg_restore`，避免误用主机上版本不匹配的客户端；只有显式设置 `BACKUP_PG_RESTORE_BIN` 时才使用指定的外部可执行文件。
- 发布前先读取承载备份目录的文件系统容量；容量门禁失败时不得启动 `pg_dump`，也不得用删除业务数据来绕过门禁。
- 备份、迁移、清理和服务健康检查按顺序记录时间、路径、文件大小、校验结果和最终状态。清理失败时保留现场并停止后续发布步骤。
- 发现空间异常增长时，先按目录和文件类型取证，再处理明确属于缓存、失败临时文件或超出保留策略的备份。业务表、容器 volume 和日志不得凭名称直接删除。
- 新增日志、导出缓存、构建缓存和临时产物时，必须同时定义大小上限或到期策略；日志通过轮转处理，清理前确认文件未被任务占用。需要长期审计的记录应单独归档，不与普通运行日志混用保留策略。
- 定期分别统计数据库、备份、日志、缓存与容器存储，记录增长趋势。迁移到其他运行环境时一并迁移这些容量门禁和保留任务，不能仅复制应用代码后遗漏清理机制。

## 整库备份保留策略

整库备份工具 `scripts/backup_retention.py` 默认只预演，不删除文件。必须显式传入 `--apply` 才能执行删除：

```bash
python scripts/backup_retention.py --backup-dir /path/to/backups
python scripts/backup_retention.py --backup-dir /path/to/backups --apply \
  --report-file /path/to/backups/backup-retention-report.json
```

`--apply` 未指定 `--report-file` 时，工具会在备份目录生成唯一的
`backup-retention-UTC-UUID.json` 报告；删除前一定先写入计划阶段，完成或失败后再更新同一份报告。

工具只管理精确匹配 `pre-migrate-YYYYMMDDTHHMMSSZ.dump` 的普通 PostgreSQL custom-format 备份。环境备份、迁移基线、专项命名、`.partial` 文件、报告和其他文件都不会被自动删除。需要长期保留的普通备份可以在 pin 清单中写入文件名，或创建同名 `.pin` / `.pinned` 标记文件；专项备份本身不进入普通候选集合。

默认保留集合为：

- 最近成功的 3 份；
- 以当前参考时间为界，每个最近 7 个日历日的最后一份；
- 当前周及之前 3 个 ISO 周中每周最后一份；
- 最早一份有效普通备份作为恢复基线；
- 所有显式 pin 和非普通专项文件。

删除前，每个候选必须同时满足以下条件：路径是备份目录的直接子项、不是符号链接、是未变化的普通文件、非空、具有 PostgreSQL custom-format 头，并且 `pg_restore --list` 校验成功。扫描到任意普通时间戳备份校验失败时，工具整体 fail closed，不删除其他备份；预演输出和 `--report-file` 报告是清理证据。`--report-file` 必须使用 `.json` 后缀，不能指向 pin 清单或任何备份；apply 会先排他写入计划报告，复核备份集合和 pin 后才允许删除，并在删除部分完成后失败时记录已删除文件。

备份写入必须使用临时后缀（例如 `.dump.partial`），并在创建临时文件前设置 `umask 077`。完成后检查非空及归档目录可解析，再通过同文件系统 rename 成最终 `.dump` 文件。`pg_restore --list` 只验证目录，不等于完整数据读取或恢复演练；删除大量历史恢复点前还应完整读取最新备份，并按风险安排隔离恢复验证。失败的临时文件不得伪装成有效备份，也不得覆盖已有文件。备份成功后、迁移继续前运行保留清理；清理报告必须留存，便于回滚和审计。

## 异地备份与恢复

本地保留点只能解决短期误删和发布回滚，不能替代异地副本。至少保留一份与应用运行环境隔离的加密副本，并定期在隔离环境执行恢复演练。异地副本的保留期限、访问权限、加密密钥和恢复责任应记录在对应运行手册中；移动或复制备份时不得把数据库 URL、密码、Cookie 或真实导出数据写入仓库。

## 数据库空间处置边界

删除数据库行只改变逻辑数据，不保证操作系统立即通过 `df` 回收空间。空间回收还受 PostgreSQL 表膨胀、索引、WAL、打开文件和容器卷层影响；处理后要分别核对数据库统计、卷使用量和文件系统可用空间。

禁止使用 `docker volume prune`、无目标范围的 `docker system prune` 或未审阅的 `VACUUM FULL` 来应急腾挪空间。前两者可能删除其他服务的数据，后者可能长时间锁表并额外消耗临时空间。需要数据库整理时，应先确认备份、锁影响、预计临时空间、执行窗口和回滚方案，再执行有范围的维护命令。

## 协作者操作要求

协作者开始涉及磁盘或备份的任务前，先阅读本规则和仓库根目录 `AGENTS.md`。报告必须区分“已扫描”“预演将删除”“实际已删除”和“文件系统已回收”；未经真实环境验证，不得声称线上空间、异地备份或恢复能力已经生效。发现路径越界、符号链接、文件变化、校验失败或容量门禁失败时，应停止删除并把证据交给主任务负责人。
