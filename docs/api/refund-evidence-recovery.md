# 退款证据与受控恢复

状态：2026-10-20 核查及修复中；不表示生产回填、财务对账或静态首版已完成。用户已授权修复及发布准备，无需 Linear。执行证据统一追加至 [开发日志](../devlog/20261019_unified_dashboard_publications.md)。

## 上游字段与内部业务语义

接口为 `GET /goodlife/v1/akte/after_sale/order/query/`。核查来源为[官方列表文档](https://developer.open-douyin.com/docs/resource/zh-CN/local-life/develop/OpenAPI/general-capabilities/groupon-refund/refund-list-query)、[官方详情文档](https://developer.open-douyin.com/docs/resource/zh-CN/local-life/develop/OpenAPI/general-capabilities/groupon-refund/after-sale-order-detail)及[官方 Go SDK](https://github.com/bytedance/douyin-openapi-sdk-go/blob/main/client/client.go)。页面内嵌 schema 也属于本次核查范围。

- `after_sale_id` 标识售后单，`refund_info_list[].refund_id` 标识子退款；订单 ID 不能代替退款 ID。
- 平台 `refund_type` 是发起来源（用户、过期自动、系统、运营、商家），与内部 `DouyinRefundEvent.refund_type` 的部分/全额枚举不同。平台字段不得直接写入内部业务类型。
- 主单状态 50、子单退款状态 500 的成功含义有官方枚举支持；二者属于不同层级，不混用枚举。
- 应退、实退、用户退款、补贴及手续费属于不同组成，不能把任意一个字段当成现有券级实收基数的扣减金额。单券、多券和次卡也不能共用未经证明的分摊规则。
- 本次查到的该端点金额说明和 SDK 整数类型没有明确货币单位。其他端点注明“分”、现有导出脚本除以 100、部分数据数值相等，都不能单独确证本端点的完整契约。
- 单位和范围未证实时保留原始数据及质量告警，不填 0，不把发起来源 2 当全额退，不制造金额转换开关绕过检查。

## 已证实的恢复风险

2026-10-20 对目标日期任务的只读有界核对：1,375 个售后单均有原始数据、均为主单成功，但业务事件缺失；包含 1,416 个子退款。1,317 个子退款能匹配现有券，99 个尚未匹配；其中有次卡子项。金额不同组成与券退款快照并非普遍一致，不能按字段名批量替换。

内部费用基数采用券级实收。初次计算取券退款快照和事件累计的较大值，但迟到事件调整依赖首次成功观察时间。已复现“券快照先扣 1,000 分，之后补同一笔事件又扣 1,000 分”的到达顺序风险。因此，事件 ID 幂等并不等于经济金额不会重复扣减。

已有调整还以事件 ID、原费用结果、费用方向组成稳定键；修正同 ID 的金额并重跑，不会自动产生正确补差。禁止删除旧调整或改成新子事件 ID 来逃避幂等键。确认、锁定、争议、发票及历史确认事实都需要保护，不能只检查当前账单的一个状态字段。

## 恢复顺序

1. 默认只读预演：限定一个来源任务、有限批次、主键游标和固定上界，记录快照摘要、可处理/阻断数量与理由，不输出原始 payload 或客户资料。
2. 先取得金额单位、退款经济口径及子单/券/次数归属的明确证据，再实现版本化适配；未满足时保持阻断。
3. 重放工具只允许明确内部契约、且不存在既有财务结果的记录进入受控写入。已有费用、调整或账单来源的记录单独列为需对账，不能调用普通重放直接补事件。
4. 正式执行需绑定预演摘要、独立修复任务和原因；行锁后重核来源哈希，分批短事务，复用既有事件仓储及影响记录。原始 payload、来源、质量历史和首次成功观察不得重写或倒填。
5. 任何新事件都要核对后续物化及结算影响，原始修复成功不能代替业务基线验收。已有财务结果的差额修复需先证明快照与事件覆盖关系，再沿受保护账单的调整/顺延规则处理。
6. 静态看板沿用 [发布门禁](dashboard-publications.md)：来源一致、首版完整、资源足够才切换 API；不因任务成功或质量告警历史仍存在而单独判定基线完整/不完整。

## 工具、并发与审计

`scripts/replay_refund_evidence.py` 默认使用数据库只读事务，必须显式给出来源、主键游标及批次上限。例如：

```bash
python scripts/replay_refund_evidence.py --source-run-id '<来源任务 ID>' --after-id 0 --batch-size 100 --max-batches 20
```

每批最多 100 行、每次最多 20 批；默认 SQL 超时 3 秒、锁超时 500 毫秒、事务上限 15 秒。输出包含固定主键上界、摘要、阻断理由及是否仍有下一批，不输出原始 payload。退出 2 表示阻断或失败，不能按“命令返回了 JSON”判为恢复完成。`financial_guard.not_checked` 明确表示尚未检查，不是没有历史财务影响。

写模式还需 `--apply --preview-file <预演文件> --preview-digest <原摘要> --repair-run-id <独立任务 ID> --reason <审计原因>`，并复核来源与所有批次参数；没有金额或范围覆盖参数。每个写事务都先获取正常 heavy-sync claim 互斥锁，再检查活动来源和其他修复，随后锁财务表和目标原始行；运行中的任务即使租约过期也不被视为已停止。每批事件、影响记录及审计进度原子提交，中途有新来源任务时停止剩余写入，不强行完成终态。

修复一旦产生影响，独立任务的顶层 `needs_downstream_processing` 在同一批事务置为 true 并持续保留，工具不会自行清除。静态发布同时检查该标记及未完成修复状态，并使用相同 claim 互斥锁；“重放成功”不能提前开放发布。后处理和财务覆盖核验完成前不得手工清空标记。

已有财务事实的订单探测采用独立等值 LIMIT 1，受 SQL 超时约束；当前部分历史表没有 order_id 前导索引，不能宣称无扫描风险。仅对其他证据已满足的记录执行财务检查，券范围上限 100，超限阻断。真实生产的 1,375 条待恢复记录在金额及范围检查处全部阻断，财务探测为零，未执行 apply。

## 旧维度任务

跨日到期的 `priority-daily-v1-dimensions-*` 重试进入正常调度，优先级低于当日日批、今日维度刷新和商品刷新，高于可选历史回补。每轮最多一个旧任务、最多检查 64 个合格候选；保留原窗口、配置、父任务身份、租约、冷却和重试次数。

`backend_aweme_export` 实际刷新当前绑定维表，不按任务日期读取历史事件。但仅凭后续任务成功不能证明原商户/筛选范围完整覆盖；若要审计取消旧刷新意图，须核实所有旧尝试在写入前失败、后续同范围来源有效及无未消费影响。通过现有取消入口分别处理子任务和只有该子任务的根计划，保留错误与审计，不能标成成功。
