# 榜单刷新、导出与保留契约

本契约对应迁移 `20261009_0062`。上线前必须先完成迁移；开发完成不代表生产已启用。

## 刷新与静态导出

- 页面保持原有五分钟请求频率；刷新发生在查询请求时，没有新增全时段计算任务。相同日期范围、产品范围、指标版本和数据模式，源数据未变化且未跨越指标时间边界时，复用已成功发布的快照，不因过去五分钟就复制一份全量结果。
- 源表的新增、修改、删除及 PostgreSQL TRUNCATE 由迁移安装的语句级触发器记录变化。计数是保守失效信号；同值更新也可能使缓存失效。新增计算依赖表时，必须同步依赖清单、新迁移和失效测试。
- 已写入的未来业务时间及待成熟指标边界也会使快照到期。不能只比较源数据更新时间。
- 导出接口 `/api/v1/dashboard/douyin-ranking/export` 读取与当前查询条件匹配的最新成功静态版本；不计算、不生成新快照；成功下载只记录该版本的访问时间，不复制榜单事实。没有对应版本时提示先刷新榜单。
- 导出内容与该静态版本一致，未刷新时不会擅自纳入之后的新业务数据。产品范围或日期范围不同，不能借用另一范围的快照。
- PostgreSQL 读取持有快照父记录锁，清理跳过正在使用的版本；计算失败或计算期间检测到源数据变化时，不发布部分结果。

## 保留与归档

普通活跃查询键保留最近两个未归档成功版本，另保留全部显式归档版本。生成不足一小时的版本暂不清理。超过三十天没有页面查询或成功导出的范围可以整体淘汰普通版本；需长期保留的正式结果必须归档。

关键业务时点由业务确定，不默认把每日每次刷新都当作永久档案。需要作为后续计算基准、正式发布依据或审计证据的结果，按 `run_id` 归档并写明原因和操作者；归档后不会随普通轮换删除。

```bash
# 使用部署环境提供的数据库连接，不把连接串或密码写入仓库
python -m scripts.ranking_retention --limit 50
python -m scripts.ranking_retention --apply --limit 50
python -m scripts.ranking_retention --archive RUN_ID --reason "结算周期确认基准" --actor OPERATOR
python -m scripts.ranking_retention --unarchive RUN_ID
```

清理默认预演；显式 `--apply` 时按单个完整版本分事务执行，限制每次最多处理的版本数。归档和解除归档是明确写操作。页面响应后触发有界后台清理，失败不得改变已返回的榜单结果；批量历史积压仍应使用维护命令分批处理并检查输出。

## 协作与维护

保留策略只作用于可重建的榜单父记录、汇总行、样本行和生命周期记录，不删除订单、线索、分配、跟进、核销和退款事实。源计数表属于缓存正确性协议，不得单独清空、回退或禁用触发器。数据库恢复必须包含源数据及对应元数据的一致恢复点。

首次启用策略前，先识别并归档关键旧版本，再预演清理。没有历史源指纹的旧版本可用于静态导出，但不能冒充输入未变的缓存命中。通用备份和磁盘处置遵循 [磁盘管理规则](../rules/storage-management.md)。

## 首次上线保护

0062 首次迁移将迁移时已存在、受管理模式（`business` / `synthetic`）的成功榜单统一标记为待复核归档（操作者 `migration:20261009_0062`），不扫描或复制样本事实。它们不参与自动淘汰，也不会因未知源指纹被误用为新鲜缓存；确认无需保留后逐版本解除归档。迁移之后新生成的普通版本执行上述两版和闲置期策略。这是有限历史集合的上线保护，不代表以后每日自动永久归档。

历史自定义模式（例如早期 `production` 标签）不转换、不删除、不纳入自动保留；其事实保持原样。
