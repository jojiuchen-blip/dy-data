# 线索中心高数据量加载与品牌署名生效设计

## 目标

线索中心在数据量继续增长时，仍能快速显示可用内容，不因后台刷新或单个接口失败而整页空白；同时确保 2026-08-06 已合入的正式品牌署名进入本次腾讯云构建并在实际页面生效。

## 已确认的基线

- 生产数据量约为 2.38 万条线索、7.1 万条分配轮次。
- PostgreSQL 指标聚合约 0.1 秒，API 端线索概览约 0.06 秒；它不是当前主要等待来源。
- `/clues/filters` 返回约 1,922 家门店，响应约 196 KB，首次进入页面时与概览请求并发发生。
- 当前 `useApiResource` 每次请求前清空旧数据，导致筛选或刷新时主内容消失。
- 当前生产包曾出现顶部“加载中”但主体“指标暂不可用”的状态不一致。
- 当前正式前端入口包约 1.39 MB（gzip 后约 456 KB），Vite 已给出大包警告。
- 品牌署名源码和测试已在 `origin/main`，但必须通过正式构建产物和腾讯云运行页面证明其真实生效。

## 方案选择

### 方案 A：只加数据库索引

不采用。数据库指标查询已足够快，无法解决旧数据被清空、筛选响应过大和状态错乱。

### 方案 B：全站一次性引入完整数据查询框架

不采用。引入 React Query 等新依赖会扩大迁移和回归范围，不能最快解决当前线索中心问题。

### 方案 C：共享轻量资源层，先接入线索中心（采用）

保留现有技术栈，增强 `useApiResource` 和 GET 客户端；把大门店列表拆为按需搜索接口；为正式构建启用安全压缩，并把重页面改为按路由加载。底层能力可复用，但本次只强制迁移线索中心。

## 详细设计

### 1. 页面资源状态

`useApiResource` 区分：

- `loading`：没有任何成功数据时的首次加载。
- `refreshing`：已有成功数据时后台刷新。
- `error`：最近一次请求失败；若存在旧数据，旧数据继续显示并提供重试。

依赖变化、手动刷新和失败均不得先清空上次成功数据。每次请求带递增序号，只有最后一次请求可写入状态，旧响应不得覆盖新筛选结果。

### 2. 请求合并和短时缓存

GET 客户端按完整 URL 合并同时进行的相同请求。门店搜索结果使用当前登录用户 ID 作为缓存命名空间，在浏览器内存中缓存 60 秒，最多保留 100 个键；登录和退出时清空缓存。概览数据只合并进行中的相同请求，不做跨刷新持久缓存，避免跟进操作后展示旧指标。

缓存仅存在当前浏览器标签页，不在 Nginx 对带 Cookie 的业务响应做共享缓存，防止不同账号的数据范围串用。

### 3. 筛选接口拆分

`GET /api/v1/clues/filters` 新增 `include_assigned_stores`，默认 `true` 保持旧客户端兼容；新线索页面传 `false`，首次只加载省、市、商品类型和状态等小型元数据。

新增：

```text
GET /api/v1/clues/filter-options/stores
  ?q=<门店名称或ID>
  &province=<可选>
  &city=<可选>
  &selected_store_id=<可选>
  &limit=50
```

接口继续执行现有账号门店范围和商品类型可见性约束，返回去重后的 `StoreOption[]`。`limit` 最大 100；空查询只返回首批结果。选中的 URL 门店即使不在首批，也应返回以正确显示标签。

门店输入框聚焦后才请求；输入使用 200 毫秒防抖。省、市筛选改变时刷新候选门店。商品类型继续默认 `all`。

### 4. 加载与错误文案

- 首次没有数据：展示固定高度的加载占位。
- 已有数据刷新：卡片继续可读，只显示“正在更新”。
- 刷新失败：显示“更新失败，当前展示上次成功数据”，保留重试按钮。
- 首次失败且无数据：才显示“线索指标暂不可用”。
- 顶部数据来源标签只依据当前页面主资源，筛选元数据后台刷新不得把主内容标成不可用。

### 5. 传输和前端包

Nginx 对 JSON、JavaScript、CSS、SVG 和文本启用 gzip，设置 `Vary: Accept-Encoding`，最小压缩长度 1 KB；不增加授权 API 的共享响应缓存。

`App.tsx` 使用 `React.lazy` 按页面拆分非当前路由，配合稳定的 `Suspense` 占位。目标是正式入口包不再包含全部后台和报表页面，且 Vite 不再对入口包发出 500 KB 大包警告；若某个独立图表分块仍超过阈值，应记录为独立异步块而非首屏阻塞项。

### 6. 品牌署名

不重新设计品牌组件。沿用 `BrandAttribution`、生成的 mask 和既有放置规则，验收以下页面：

- 登录页底部；
- 左侧导航底部；
- 首页底部；
- 个人设置区；
- CLI/MCP 授权页。

正式构建前运行 `build:brand-attribution`，检查生成文件与源码一致；构建产物必须包含 `dc-brand-attribution` 和正式 SPACE mask。腾讯云部署后用真实页面 DOM/截图核对，不以 Git 提交存在代替生效证据。

## 性能与资源验收

- 已缓存或后台刷新时，页面不得清空已显示指标。
- 同一 URL 的并发 GET 在网络层只发出一次。
- 首次 `/clues/filters?include_assigned_stores=false` 响应不包含全量门店，目标未压缩体积小于 30 KB。
- 门店搜索单次最多 100 条，默认 50 条，且账号范围不越权。
- 概览 API 生产 p95 小于 500 ms；门店搜索生产 p95 小于 700 ms。
- 页面 LCP 目标小于 2.5 秒，INP 小于 200 ms，CLS 小于 0.1。
- 压测和同步并行时，腾讯云整机 CPU 与内存均不持续超过 70%；超过即停止扩大变更。
- 前后端测试、正式构建、品牌测试、数据与权限回归全部通过。

## 发布与回滚

1. 在隔离分支生成带唯一标签的 API/Web/Proxy 镜像。
2. 测试环境运行 API、UI、权限、性能和品牌验收。
3. 记录腾讯云当前镜像标签和容器配置。
4. 仅替换 API/Web/Proxy；不删除业务数据，不启动已关闭的定时同步。
5. 健康检查、数据核对、资源监控和页面验收均通过后保留新版。
6. 任一关键检查失败，恢复上一组镜像标签并重新检查健康。

## 非目标

- 本次不分库分表，不引入 Redis，不迁移全站所有页面。
- 本次不修改业务数据，不恢复或重启定时同步任务。
- 本次不重新设计品牌标识，只确保已批准版本进入正式部署。
