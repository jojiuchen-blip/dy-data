1. 账单总额；
2. 已确认金额；
3. 已开票金额；
4. 审核通过/已结算金额；
5. **待开票金额**。

“审核不通过金额”不再单列为指标卡，但其审核状态、原因和重开记录仍必须在推广发票记录/详情中可查询。第五项“待开票金额”由正式 API 作为唯一权威金额返回，必须覆盖：

- 已确认且当前仍待开票的金额；
- 审核不通过后已经整体释放、可重新开票的金额。

前端不得把两个来源的金额本地相加，以免同一分配金额被重复计算；正式 API 必须以当前有效版本、账期分配与重开关联关系去重后提供 `pendingInvoiceAmount` 及可审计的来源拆分。该口径覆盖冻结原型五卡和 DYDATA-19 §7 的呈现冲突；是否与 §7 的通用“待开票金额”公式完全一致，须在后续 API 合同中以服务端计算结果证明。

### 8.3 “发票号当前仍被账期限定”的含义

当前实现的请求必须先带一个 `month`，再带 `invoiceNumber`。例如一张发票实际覆盖了 `2026-07` 与 `2026-08`，用户在页面的账期筛选为 `2026-09` 时，即使输入完全正确的 20 位发票号，服务端也会先排除它并返回空结果。

已确认的目标顺序应为：**绑定门店和权限范围 → 服务端精确匹配发票号 → 对命中结果分页**。账期筛选如保留，只能是显式附加条件，不能让精确发票号被默认账期先排除。这就是“跨全部授权账期精确查询后分页”。该项仍需后续门店端 API 合同与真实 GWT，当前不做实现。

### 8.4 门店端 UAT 预览：获准范围与制作方案

用户已允许提供门店端 UAT 页面供查看，但这不改变“原型冻结 → 合同矩阵 → 用户验收 → 实现”的门禁。因此 UAT 只能是**只读验收预览**，不是正式页面、不是生产部署，也不调用写接口。

**【用户确认，2026-08-29】** 按以下方案制作只读 UAT 验收预览：

1. 用主系统 Shell、视觉 token、响应式规则，提供上述五个二级导航页的独立 UAT 路由；
2. 严格按本节的模块顺序、删减项、两栏/并列关系渲染；
3. 只显示真实 API 已返回的数据；若无数据，显示“暂无数据”“尚未生成”或“待确认”，绝不放入测试账期、演示金额、演示状态、预览标签或可写入动作；
4. 在有正式可确认推广账单时才显示确认后的跳转关系；无正式账单时按钮不可伪造成功，跳转关系以 GWT 合同记录为证；
5. 产出 1440、768、390 三档并排截图，以及无数据/有数据/错误的 Given–When–Then 截图索引；不改 `/finance/*`、接口、权限、测试或生产配置。

该预览的验收目标是让你先确认结构、模块顺序、字段位置、空态与跳转关系；业务数值和状态仍以正式 API 为唯一来源。UAT 设计规格将先写入 `docs/superpowers/specs/` 并由用户审阅；在规格审阅通过、开发计划一致性恢复前，不进入正式页面实现、部署或关闭 Issue。
