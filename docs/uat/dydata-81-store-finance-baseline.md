## 2. 三页共同结构

临时看板共同结构为：品牌/当前门店/账期 → 门店结算侧栏 → 三个页面入口 → 面包屑/页面标题 → 月度节奏 → 当前状态通知 → 页面主内容。

正式映射固定为：现有系统 `Shell` 左侧“订单分佣”一级入口 → 顶部文字二级导航 → 页面 `page-heading` → 共享月度节奏 → 页面状态与内容。临时看板的独立顶栏、独立侧栏、角色切换、主题切换和本地按钮切页均不复制。门店端二级导航仅保留全国门店榜单、单店分账、订单费用明细、开票确认、发票状态查看；“SAP 建议”整块移除，门店角色不得直接访问 `/finance/stores`，财务/管理员端对应能力不受影响。

## 5. 冲突与批准差异

| ID | 冲突 | 权威裁决 | 本轮处理 |
|---|---|---|---|
| D-01 | 临时看板要求“不含税金额、税额、价税合计关系及税额容差”，真实 `POST /promotion-invoices` 只接收总金额，不保存两项拆分 | 用户最新确认要求门店填写；API/Foundation 仍高于临时字段展示 | 门店手工填写不含税金额/税额/价税合计，按三位小数计算后四舍五入到分并校验金额关系，允许 0.01 元容差；不按 6% 自动拆分，不向 API 提交或伪造未入契约字段；需持久化拆分时由后续 API 扩展 |
| D-02 | 临时看板状态页展示审核失败原因；当前 detail API 读取了状态事件，但响应未暴露 `resultReason/businessDate/businessAmountCent` | Schema 有字段，运行时 API 缺响应字段 | 状态页在失败时显示“暂无审核原因”；不从文本或状态猜测；需 API 扩展另建后续项 |
| D-03 | 临时看板展示红冲/作废场景；现有正式运行时已按后续 DYDATA-19 契约提供真实生命周期登记与替换闭环 | 现有 `StoreInvoicePage`、真实发票生命周期 API、回归测试 | 本轮不重做、不删减该既有能力；默认页面仍以开票登记与状态查看为主，生命周期操作继续使用真实接口并保留历史记录 |
| D-04 | 临时看板三页共用 `/` 本地状态 | 正式系统稳定 URL 规则 | 使用 `/settlement`、`/settlement/invoice`、`/settlement/invoice/status` |
| D-05 | 临时看板希望跨账期按发票号码精确查找；当前 `GET /promotion-invoices` 仍要求账期参数 | 真实 API 契约高于看板交互；跨账期查询需新增后端契约 | 当前状态页仅透传当前账期的服务端精确筛选；已建立 DYDATA-84，未使用前端本地过滤或伪造跨账期结果 |
